# Shared research areas and active-call classification

The primary vocabulary is the 528 imported discipline labels in `catalogue_areas`.
The nine broad imported subjects remain separate. Picker sections do not imply
new parent-child relationships. `CANONICAL_RESEARCH_AREAS_ENABLED=true` enables
the shared provider; its default is off until migration and rehearsal finish.

## Classifications and compatibility

Calls, saved interests and departments can have several standard areas. Users
can also save their own research description without choosing a classification.
Voyage supplies optional related-area suggestions for them to confirm. Existing
free-text profile matching remains available without a canonical selection.

Accepted call revisions take precedence over source index and legacy bridges.
The original call, source classifications and legacy taxonomy rows remain
stored. Source imports and their embeddings are not regenerated by this job.
The same effective call areas drive directory/AI filters, area statistics and
research-area displays. `All disciplines` calls remain discoverable under a
specific research-area filter, while country and eligibility checks still apply.
Counts deduplicate a call that has several source labels.

Existing departmental scopes are preserved using the already-reviewed import
crosswalk in its original direction: new label to old area code. This does not
infer a one-to-many inverse mapping for old preferences. The derived
`research_area_legacy_targets` table lets an existing medical department match
a newly classified hematology call without retaining an erroneous engineering
tag. Old department rows, structure IDs, assigned work and triage stay intact.
User-facing department selections exclude derived routing compatibility targets.

The migration adds four tables and four views only. No funding/profile column
is altered, no old classification is deleted, and no notification is emitted.
Backfill acceptance does not call the ingestion, publication or school-allocation
pipelines. Normal new intake continues its existing workflow, using the shared
classifier when enabled. Human classifications require explicit review.

## Embedding and review pipeline

1. Embed each standard area once with `voyage-4-large`, 1,024 dimensions.
2. Embed the call title, research purpose and bounded existing topic hints as
   a query. These query vectors do not replace the stored full-call vectors.
3. Retrieve about 20 candidates, adding literal topic matches and the broad
   `All disciplines` / `Interdisciplinary` options. Expand once to 48 if needed.
4. Ask `gpt-5.4-mini` to validate the actual funded research, with the old topic
   hints excluded from the verification evidence. Geographic conditions,
   administration and incidental words do not establish research disciplines.
5. Strict structured output selects request-local area codes and source-passage
   codes. Server lookups expand these into real IDs and original source text.
   This prevents a mistyped hash or invented quotation reaching an accepted
   mapping. At most eight supported areas are permitted. Ambiguous/unknown
   results remain pending.
6. Before acceptance, lock the call, recheck its input hash and live eligibility,
   validate IDs/evidence again, protect existing human decisions, and retain
   the prior classification revision. Revocation restores compatibility reads.

Similarity is a ranking signal, not a measured probability of correctness.
Source text is untrusted input, not instructions. The classifier uses Voyage
only; it fails instead of falling back to another embedding provider.

## Operator workflow

`scripts/classify-active-research-areas.ts` estimates by default. `--generate`
explicitly enables paid preview generation and checkpoints a private manifest
and the vector cache. A shared US$2 allowance covers indexing and review;
network failures retain a conservative cost reservation rather than silently
resetting the allowance. The manifest records usage and prompt version.

`scripts/apply-active-research-areas.ts` is also a preview by default. It needs
an exact `--confirm-target`, manifest and matching vector cache. Production
application additionally requires a recent backup checksum, verified restore,
successful classification rehearsal, and the actual Grapsi checkout/database.
It never makes model calls. Calls that closed or changed are skipped. Reviewed
manual selections require both a reviewed-call list and the explicit manual
confirmation flag. Pending proposals are visible at
`/admin/funding/research-area-review`; approval requires fresh superadmin
authentication and the normal shared catalogue guard.

The active-only scope excludes imported rows, unpublished/inactive calls,
future openings, closed/unknown dates, and rolling flags with expired deadlines.
Do not automatically delete or close a recurring programme on a date conflict.
Closed/expired record deletion is outside this release.

## Verification and rollout

- Run the canonical unit tests, typecheck, lint and additive migration check.
- `scripts/verify-canonical-research-areas.ts` uses a disposable local database
  to exercise source preservation, corrected searches, reconciled counts,
  broad calls, old department compatibility, new department selections, custom
  interests, stale proposals, closed calls and manual-decision protection.
- Capture a focused backup that explicitly includes department mappings and
  org structure. Restore it to a dedicated `grapsi_area_rehearsal_*` database.
  Rehearse migration, index, application and HTTP/UI checks there.
- Compare preservation fingerprints, verify private/authenticated responses,
  and enable the feature only after rehearsal. Restart only `grantmentor`.
- Retain backup and previous build. To roll back behaviour, set
  `CANONICAL_RESEARCH_AREAS_ENABLED=false` in the environment and update that
  flag when restarting only `grantmentor`. Keep additive tables and history;
  never restore a full backup over newer production work as an app rollback.
